# Project context for future agents

- Purpose: German private diary and analysis web app for reviewing meal-specific insulin factors from FreeStyle Libre 3 Plus CGM data and manually injected Fiasp. Development discussion and code can be in English; all user-facing UI text is German.
- Nightscout is the exclusive source of truth for CGM readings, carbs, injections and the time-specific correction-factor (`sens`) schedule. SQLite mirrors source data, caches the current Nightscout profile for local analyses and stores versioned calculation-model settings. Apply the current profile schedule to all analyses; do not reconstruct historical profile schedules. Calculated meal factors are never written to Nightscout; each calculated diary day is stored in SQLite (`day_results`) with a fingerprint of everything it reads plus a hash of the app's code, and is recalculated whenever that fingerprint changes (backend rework 2026-10, plan in project files `architektur/backend-umbau.md`). Credentials and app login come from deployment environment variables, never tracked files. SQLite remains on the persistent data mount.
- Insulinfaktor means **IE per KE**, with 1 KE = 10 g carbohydrate (the user's Libre diary also uses 1 BE = 10 g). Korrekturfaktor is separate, time-specific **mg/dL per IE**. Nightscout I:C is g/IE = 10 / (IE/KE).
- One factor is calculated for each breakfast, lunch or dinner window. Sum **all** recorded carbohydrate events and **all full rapid-insulin IE** from meal start up to, but not including, the endpoint. Split boluses and later corrections count in full even minutes before the endpoint; prior injections and basal insulin do not count. Do not revive the former triangular Fiasp action weighting; legacy peak/duration settings are ignored.
- Default endpoint: meal start + 180 minutes. Every rapid-insulin dose inside the window (before the next main meal) extends the endpoint to that dose + 180 minutes, so late corrections get a full window to act. If the next main meal is >120 minutes after meal start and before that (possibly extended) endpoint, use the last valid CGM value within 15 minutes before it. If a second main meal cannot be separated this way, show a blocker. CGM values at exact endpoints are linearly interpolated with a maximum 15-minute surrounding gap.
- A user can persist a manual window per meal in SQLite (`analysis_windows`: meal start − 2 h ≤ start ≤ meal start + 2 h, end ≥ max(meal start, start) + 30 min, at most 10 h long). It replaces the automatic start/endpoint for that meal only; the meal's own entry (carbs and its bolus) always counts even if the start lies after it; the same half-open counting, full-dose rule and second-main-meal blocker still apply. It is never written to Nightscout.
- A new diary carb entry < 120 min after the previous main meal start (across the clock-based breakfast/lunch/dinner boundary), or inside the (extended) window of a main meal of the same kind, is a snack of that meal. The entry form shows this as a chip the user can flip to "own main meal" (`[DA2:meal]` marker), which keeps it a separate root. Each meal kind counts at most once per day (user request 2026-10-14): a diary carb entry whose clock-based kind already has a main meal that day is a snack, of the preceding meal by the rules above or else of no meal, and cannot be flipped to its own meal. A new diary carb entry below 20 g that would start a main meal defaults to a snack of no meal (user request 2026-10-19, entry.SMALL_SNACK_GRAMS; a bite before sport must not take the day's meal) and can be flipped to its own meal. A stored diary snack (`[DA2:snack]`) whose meal became a snack of no meal this way is classified afresh on day load and can become the main meal itself (13.10.: 12:20 is lunch); other stored snacks stay snacks.
- Day type (work/free) applies to breakfast: manual per-day choice (`analysis_day_types`) > open vacation period (`vacation_periods`, toggled in settings) > Mon–Fri work. Before breakfast end, dose help uses the median breakfast IE/KE of that day type from the past 28 days when ≥3 valid non-excluded meals exist, else Nightscout I:C.
- With carbs, dose help uses only the calculated auto factor (user request 2026-10-06) and shows three suggestions with it: normal (corrects to `dose_target_mgdl`), cautious (corrects to `dose_cautious_target_mgdl`, default 140) and carbs only (carbs plus sport, no BG correction, needs no fresh CGM). While auto has <4 meals the breakfast day-type median or Nightscout I:C stands in, named in the factor line. Without carbs: normal and cautious correction. Auto uses the `auto_percentile` (25–50, default 37.5) of valid non-excluded IE/KE of the current meal kind (by clock; breakfast filtered by day type) from the past `auto_lookback_days` (8/15/30, default 30; 8 keeps the previous Saturday on Sunday; a stored 14 becomes 15, 21 or 28 becomes 30), each weighted 0.5^(age/`auto_half_life_days`) (default 7; weighted quantile = linear interpolation at (n−1)×p for equal weights, app/forecast.py), needs ≥4 meals. The former day shift (Tageslage) and equally weighted method were removed at the user's request. `auto_method` = `percentile` (default) or `surcharge` (approved by Philipp 2026-10-07, analysis in /mnt/project-files/analysen/formel-grundbedarf.md): each main meal has a meal surcharge Z = `auto_surcharge_mgdl` (fat/protein, default 40, 5–150), scaled by min(1, carbs/40 g); past factors lose 10·Z·share/S before the percentile, and the dose adds Z·share/KF IE once per main meal (never for a snack the entry form assigns to a meal). The analysis page has two sub-tabs (user request 2026-10-08): Werte (period-based values) and Automatik: a worked example per meal kind (factor, typical meal, KE × factor + surcharge), current strategy vs. the trade-off line of all option combinations (not beaten on both <80 and >160; forecast.tradeoffs), one row per setting with only that setting varied (percentile 25/30/35/40/45/50, surcharge off/20/40/60/80, half-life, lookback; each row on the meals all its options can predict; verdict better/shift/none beyond max(2 meals, 5 %); forecast.tuning), and an "Übernehmen" per option that saves the setting change the server attached. Collapsed below it shows the color-coded backtest matrix over the meals of the last 90 days, independent of the analysis period (lookback 8/15/30 × half-life 1/2/3/5/7/14 × 25 %/configured/50 %/configured + surcharge, all on the same meals; best cell = most in range, then fewest <80, highlighted per lookback period and overall): simulated endpoint BG = `dose_target_mgdl` + (F − P) × Σ[g × KF]/10 (only the factor error; never add the measured g3, F already contains it) counted <80 / 80–160 / >160 mg/dL (fixed; Nightscout target range stays 80–180), plus typical factor deviation. The surcharge column predicts P = percentile of (F − 10·40·share/S) + 10·40·share/S of the tested meal (the former Zielband column was replaced at the user's request). The diary shows only the factor. An info-only analysis tile shows the work-stress surcharge for breakfast only (user request) over 30 days with free days as the base, work = free × (1 + surcharge) (overall median work ÷ median free − 1, plus per free day: median breakfast on the 2 nearest work days before and 2 after, ≤7 days away, ≥2 values, ÷ free factor − 1); it changes no suggestion. Lower IE/KE = less insulin = cautious side.
- Lower target (user request 2026-10-14): `dose_low_target_mgdl` (default 100, 60..`dose_target_mgdl`, equal = off) adds a "Tiefer" option (variant `low`) correcting the normal forecast to it, offered only without carb uncertainty: no carbs, or ≤30 g not marked unsure and not fat-rich; no open or active split; BG ≥70 and not falling; 6–20 h local; <150 mg/dL still acting (insulin + carbs + surcharge) or last carbs and rapid dose ≥2 h ago ( analysis 2026-10-14 in /mnt/project-files/analysen/tiefer-zielwert.md: by day with little acting no extra lows down to 100, all lows after 19:50). Normal stays the default; a hint names why it is withheld (app/dosing.py `low_blocked`, app/services/entry.py).
- Dose help subtracts what still acts (user request 2026-10-08, analysis in /mnt/project-files/analysen/fiasp-wirkkurve.md, app/on_board.py): rapid insulin of the last 6 h with Loop's Fiasp curve (exponential, peak 55 min after 10 min delay, 6 h; only here, never in the meal factor) × KF at the dose; carbs absorbed linearly over 2 h (≤40 g) to 3 h (≥100 g), the fat mark does not stretch them (re-estimated 2026-10-22, Philipp's go, /mnt/project-files/analysen/pruefstand-2026-10/annahmen.md), valued at the Automatik factor of their meal kind (else Nightscout I:C) × KF; with the surcharge method each main meal's surcharge × share acts linearly 2–5 h after its start (6 h with the fat mark). Normal (and carbs only) corrects the full forecast BG − insulin rest + carbs/surcharge rest; cautious uses that forecast minus its typical miss (60 mg/dL), at least the BG where the rests only cancel active insulin, and the cautious target (user report 2026-10-08: rests that only cancelled insulin gave 0.5 IE vs. 7 IE normal mid split bolus); below 70 mg/dL the same forecast applies (the former guard that only let the rests cancel active insulin was removed at the user's request 2026-10-23: it ignored a hypo snack and still subtracted the full correction, 0.5 instead of 1.5 IE for 34 g at 68 mg/dL). The diary's "Jetzt" overview shows a "Wirkt noch" card (lowers / raises / expected with its likely range by how much still acts: <40 mg/dL −30..+30, 40–150 −50..+60, ≥150 −75..+90, on_board.FORECAST_BAND, analysis 2026-10-11 in /mnt/project-files/analysen/fruehprognose.md; calculations keep the expected value; hint within 90 min after a main meal) from the preview's `on_board`. Curve shape, absorption times and surcharge window are re-estimated offline by Claude, not in the app. "Tag durchgehen" has a "Wirkungen über den Tag" card (/api/day/effects, app/services/effects.py): measured BG against the model from the BG 3 h earlier (− insulin acted + carbs/surcharge acted, same model, Automatik factor of that day), and how strongly carbs/surcharge raise and insulin lowers (mg/dL per h, 5-min steps), with mean and largest miss (≥40 mg/dL).
- Split bolus (user request 2026-10-08, app/split.py): from `split_min_grams` (default 80, 0 off) carbs on a main meal (never a snack) the entry form preselects a "Split" chip; each option then shows `split_first_percent` (default 60, rounded to 0.5 IE) now and the rest at meal + `split_delay_minutes` (default 120). Saving today stores the chosen option's full dose − entered IE as `[DASP:<IE>@<min>]` in the meal's Nightscout note. The plan stays open until a rapid dose >15 min after the meal or 3 h past due; meanwhile the "Wirkt noch" card names it (not in the forecast) and an entry without carbs offers a "2. Teil" option first, next to normal/cautious from the current forecast. Dynamic second part (Philipp's approval 2026-10-22, analysis in /mnt/project-files/analysen/pruefstand-2026-10/split-bolus.md, split.timing): its amount is the current forecast's correction (= normal; the planned IE only as orientation, or as amount without fresh CGM); it is due early 60 min after the meal until 15 min before the planned time when BG ≥180 and rising ≥15 mg/dL per 15 min, and at the planned time it waits while BG <110 or falling >5 mg/dL per 15 min, at most 60 min. The split push follows that state (one per plan, naming forecast and planned IE).
- Philipp does not review code: once CI is green, Claude merges its own PRs (user statement 2026-10-08).
- Model equation: IE/KE = 10 × (ΔG + confirmed exercise glucose drop + Σ[rapid IE × time-specific KF]) / Σ[carbs in g × time-specific KF]. Sport counts automatically (user request 2026-10-22, analysis /mnt/project-files/analysen/pruefstand-2026-10/gym.md): each Exercise session lowers glucose by its drop (the setting `sport_effects_mgdl` of its kind, or Philipp's own value for that session stored locally in `sport_session_effects` by Nightscout id, set in the sport entry form or on the session in "Tag durchgehen"; 0 = none) linearly from its end over its kind's duration (`sport_durations_minutes`, default 300, 30–1440; user request 2026-10-22; app/on_board.py `sport_remaining`); a session entered up to 6 h ahead counts in full. It is part of what still acts: "Wirkt noch", every dose option incl. pure corrections, the early warnings and the day's effects chart. The meal factor's drop is each session's share acting between window start and endpoint × its drop, applied without confirmation; a meal can still take its own value (`affected`) or "Kein Einfluss" (`unaffected`), "Automatisch" returns to the curve. The entry form no longer asks about sport at meals, and sport is never an open review item. `sport_lookback_minutes` only links sessions to meals in the sport analysis. Internally the drop is positive; racing (Rennsport, adrenaline) is a sport type whose default drop is negative (a BG rise). The UI shows the signed BG change (−40 lowers, +40 raises). Use Decimal arithmetic and show the inputs, endpoint, doses, assumptions and equation. Full effect of late insulin, full carb effect by the endpoint, and no background glucose drift are **model assumptions**, not physiological facts or dosing advice.
- Basal is the one injection stored locally first (`basal_doses`, user request 2026-10-07) and mirrored to Nightscout as a `Note` with `basal_units` and `[DA2:basal]`, never with an `insulin` field (Nightscout IOB and the meal factor must not count it). Unsent doses are retried on day load; a synced dose missing from a fresh Nightscout read is dropped; untracked Nightscout basal notes are adopted. Before breakfast end the entry form offers a preselected chip with `basal_default_units` (default 17, 0 disables) while the day has no basal; a separate Basal entry mode records any amount. Groundwork for adjusting basal automatically later.
- Carb entries can carry a three-level carb certainty `[DAQ:weighed]` (gewogen), `[DAQ:known]` (halbwegs sicher: known dish or FDDB AI), `[DAQ:unsure]` (no serious estimate; older unsure marks keep this meaning), API field `carbs_certainty`, plus the meal factors `[DAQ:fat]` (fett-/eiweißreich) and `[DAQ:alcohol]` (Alkohol, user request 2026-10-14; API field `alcohol`) in the Nightscout note, picked as icon chips in the entry form and shown as icons on the meal, entry and recent chips; a meal shows the least certain level of its marked counted carb entries and each factor when any entry has it. They are recorded and exposed via the read API only and change no calculation until Philipp approves a use.
- Eating places (user request 2026-10-14; background: lunches away from the canteen needed clearly more IE/KE): a place is a chip (Kantine, Restaurant, Zuhause) with any number of spots (each a centre holding positions within a fixed 150 m; no radius setting, user request), and a "Schnellauswahl" switch: quick places get their own chip in the entry form, the others sit behind "Weitere", so one chip can gather many restaurants while a regular one keeps its own (`places`, `place_spots`, app/places.py, app/services/places.py). For a carb entry timed within 30 min of now, the browser position (fix within 30 min of the entry time, refreshed on save when older than 2 min; accuracy ≤250 m) preselects the chip of the nearest spot holding it; the user can flip it. Such a position is always stored with the entry (user request 2026-10-15; a coarser one too, with its accuracy, but never matched or grouped), and a chip picked for a precise position that fits no spot gets it as a new spot. Position and place are stored per diary entry by its `[DAE:…]` event id in SQLite (`entry_locations`), never in Nightscout. Positions matching no spot show in settings as grouped "Unbekannte Standorte" that can join an existing chip or become a new one; adding a spot assigns waiting positions inside it, deleting a place makes its entries unknown again. The edit dialog sets a place afterwards; meals show their own entry's place (else the first counted carb entry's), and an entry inside a meal in "Tag durchgehen" shows its place and carb certainty only where they differ from the meal head (user request 2026-10-21); read API `place` on meals and treatments, MCP `place` by name. Recorded only, changes no calculation until Philipp approves a use.
- Blood glucose measured by hand (user request 2026-10-11, sensor failure): the entry form's "BZ blutig" field (open by itself while there is no fresh CGM value) and MCP `finger_mgdl` save a Nightscout `BG Check` (glucoseType Finger, mg/dL, `[DAE:…]`), also without carbs or insulin. Dose help uses a BG Check (or the typed value at the entry time) as start glucose when it is newer than the latest CGM value, same 15-minute freshness, no trend. When the meal-window start has no interpolable CGM value, the nearest BG Check within 15 minutes is the meal factor's start glucose (`g0_source` = finger, named in the assumptions; user request 2026-10-11); otherwise CGM always wins. The CGM curve, endpoints and other analyses never read it.
- An entry is always timestamped now unless the user changes the time on purpose (user request 2026-10-08). The manual time is dropped after a saved entry, a day or view change, or 10 minutes without touching the entry form; while it is untouched the field follows the clock (refreshed every 30 s and when the tab becomes visible again), so a stale timestamp cannot ride along on the next entry.
- Read API for scripts and agents (user request 2026-10-07): `GET /api/v1` (index), `/api/v1/{meals,window-events,entries,treatments,basal,data,profile}` with `?days=N` (default 30) or `?from=&to=` (tables in app/tables.py), from SQLite only; it replaced the former ZIP export (removed 2026-10-09 at the user's request) and is how data reaches offline formula work; never commit fetched personal data. Auth: `Authorization: Bearer <API_READ_KEY>` from the deployment environment (≥32 chars, Philipp sets it in Coolify; no key logic in the app), or the browser login. The key never opens other endpoints or POSTs; write access would need its own variable and Philipp's approval.
- MCP for a conversational agent (user request 2026-10-08, docs/mcp.md): `POST /mcp` (Streamable HTTP, JSON responses only, app/mcp.py) with tools in app/services/agent_tools.py that only map arguments onto entry.preview / entry.save, basal and the diary, so every rule stays where the entry form has it; never add dose or factor logic there. Off unless `MCP_API_KEY` (≥32 chars, separate from the read key) is set; auth is that key as Bearer or OAuth 2.1 for the Claude apps (app/oauth.py: app password confirms, stateless tokens signed with a key derived from `MCP_API_KEY`, redirects only to Claude's callback and loopback). Saving skips the UI's tapped-suggestion check: the agent records the dose Philipp says he injected.
- The URL never carries a day (user request 2026-10-16: an old link or reloaded tab must not open an old day for new entries). The URL holds only view and analysis tab; a chosen day lives in page memory, and a reload, a new visit or 30 minutes without touching the page (web/app.js `DAY_HOLD_MS`) brings back today.
- Page roles (user request 2026-10-14, concept in project files `architektur/ux-tag-und-analyse.md`): "Tag durchgehen" is the cockpit for reviewing one day and the only place a day's data is maintained (edit/delete entries, sport per session and per meal incl. "Kein Einfluss", manual window, exclusion, day type Arbeit/Frei); its check list (day payload `review`, `meal.review`) counts blocked meals. "Analyse" evaluates several days and is read-only except exclusion and day type; its sport column only shows the state and links to the meal's day. "Jetzt" holds entry and dose help; its chart is called "Verlauf".
- "Zu erledigen" (user request 2026-10-21, app/services/inbox.py, GET /api/inbox, POST /api/inbox/seen): a general hint list above the diary's two panels for things that need an action, meant to take further kinds later (e.g. a better factor found). The first kind is a finished meal (window end passed, not excluded) of the last 7 days whose `review.open` is not empty (blocked factor); a click opens "Tag durchgehen" at that meal and stores the hint's key (`inbox_seen`), so it folds away under "schon angesehen"; it is gone once the action is done. The key holds the open reasons, so a new reason highlights again. The header shows "N zu erledigen" on every page while new hints exist. "Abmelden" sits at the end of the settings, not in the header (user request 2026-10-21).
- web/app.js only draws: every domain rule (snack assignment, sport/basal/day-type chips, dose options and the tapped-suggestion re-check, meal windows and block grouping, CGM colours, target band, interpolation and trend, manual-window limits and totals, matrix best cells) lives in app/ and reaches the page as view data (/api/entry/preview, /api/entry, the day payload, /api/analysis/window-editor and /window/preview, the summary). Add new rules on the server, not in the browser.
- Push reminders (user decision 2026-10-09, research in /mnt/project-files/analysen/benachrichtigungen.md, app/services/notifications.py, app/ingestion/pushover.py): Pushover with `PUSHOVER_APP_TOKEN`/`PUSHOVER_USER_KEY` from the deployment, priority 1. Kinds: forgotten basal (from breakfast end, today has no basal), a due second split part (split.open_plan with split.timing early or due, not injected), and since 2026-10-11 (Philipp's go, analysis in /mnt/project-files/analysen/fruehprognose.md) low/high early warnings (app/glucose_alerts.py: 6–23 h local, "Wirkt noch" model plus the last 15 min's model miss fading over 45 min (review 2026-10-22, /mnt/project-files/analysen/alarme-2026-10.md; nights stay off at Philipp's choice), forecast for the next 60 min < 70 or > 250 mg/dL, no low warning within 30 min after a carb entry of at least 20 g, at most once per hour per kind). Each kind has its own Pushover priority −2..2 (default 1; 2 = emergency with retry 60 s, expire 30 min), set in settings. The background job checks after each round only when today synced without error, sends each reminder once (`notifications_sent`; warnings once per hour), retries a failed send next round; kinds switch on/off in settings (`notification_settings`). Optional `APP_HEARTBEAT_URL` is pinged after each error-free round for an external watchdog. Further alarm kinds need Philipp's go.
- A background thread (app/services/background.py) mirrors yesterday+today from Nightscout every `APP_SYNC_MINUTES` (default 2, 0 off) and checks reminders every round, but precomputes stored days and analysis pages only when yesterday's or today's fingerprint changed (user request 2026-10-12); the mirror rewrites a day's rows only when Nightscout returned something different, and the sync time is not part of a day's fingerprint. Page requests never wait on Nightscout (user request 2026-10-22): /api/day, the entry preview and the dose help read the local copy while `day_view.mirror_current` holds (synced within one round + 1 min and after this process last wrote to Nightscout); "Aktualisieren" sends `refresh=1`, own entries still sync on save. "Wirkungen über den Tag" is stored in `summary_results` (`effects:<day>`, fingerprint = its end + the fingerprints of the day and its lookback days); for today it ends at the last sync and the background job stores it every round.
