# Project context for future agents

- Purpose: German private diary and analysis web app for reviewing meal-specific insulin factors from FreeStyle Libre 3 Plus CGM data and manually injected Fiasp. Development discussion and code can be in English; all user-facing UI text is German.
- Nightscout is the exclusive source of truth for CGM readings, carbs, injections and the time-specific correction-factor (`sens`) schedule. SQLite mirrors source data, caches the current Nightscout profile for local analyses and stores versioned calculation-model settings. Apply the current profile schedule to all analyses; do not reconstruct historical profile schedules. Calculated meal factors are recomputed, not written to Nightscout. Credentials and app login come from deployment environment variables, never tracked files. SQLite remains on the persistent data mount.
- Insulinfaktor means **IE per KE**, with 1 KE = 10 g carbohydrate (the user's Libre diary also uses 1 BE = 10 g). Korrekturfaktor is separate, time-specific **mg/dL per IE**. Nightscout I:C is g/IE = 10 / (IE/KE).
- One factor is calculated for each breakfast, lunch or dinner window. Sum **all** recorded carbohydrate events and **all full rapid-insulin IE** from meal start up to, but not including, the endpoint. Split boluses and later corrections count in full even minutes before the endpoint; prior injections and basal insulin do not count. Do not revive the former triangular Fiasp action weighting; legacy peak/duration settings are ignored.
- Default endpoint: meal start + 180 minutes. Every rapid-insulin dose inside the window (before the next main meal) extends the endpoint to that dose + 180 minutes, so late corrections get a full window to act. If the next main meal is >120 minutes after meal start and before that (possibly extended) endpoint, use the last valid CGM value within 15 minutes before it. If a second main meal cannot be separated this way, show a blocker. CGM values at exact endpoints are linearly interpolated with a maximum 15-minute surrounding gap.
- A user can persist a manual window per meal in SQLite (`analysis_windows`: meal start − 2 h ≤ start ≤ meal start + 2 h, end ≥ max(meal start, start) + 30 min, at most 10 h long). It replaces the automatic start/endpoint for that meal only; the meal's own entry (carbs and its bolus) always counts even if the start lies after it; the same half-open counting, full-dose rule and second-main-meal blocker still apply. It is never written to Nightscout.
- A new diary carb entry < 120 min after the previous main meal start (across the clock-based breakfast/lunch/dinner boundary), or inside the (extended) window of a main meal of the same kind, is a snack of that meal. The entry form shows this as a chip the user can flip to "own main meal" (`[DA2:meal]` marker), which keeps it a separate root.
- Day type (work/free) applies to breakfast: manual per-day choice (`analysis_day_types`) > open vacation period (`vacation_periods`, toggled in settings) > Mon–Fri work. Before breakfast end, dose help uses the median breakfast IE/KE of that day type from the past 28 days when ≥3 valid non-excluded meals exist, else Nightscout I:C.
- Dose help shows three suggestions: normal (`dose_target_mgdl`), cautious (`dose_cautious_target_mgdl`, default 140) and auto. Auto uses the `auto_percentile` (25–50, default 37.5) of valid non-excluded IE/KE of the current meal kind (by clock; breakfast filtered by day type) from the past `auto_lookback_days` (8/15/30, default 30; 8 keeps the previous Saturday on Sunday; a stored 14 becomes 15, 21 or 28 becomes 30), each weighted 0.5^(age/`auto_half_life_days`) (default 7; weighted quantile = linear interpolation at (n−1)×p for equal weights, app/forecast.py), needs ≥4 meals, and corrects to the normal target. The former day shift (Tageslage) and equally weighted method were removed at the user's request. The analysis page shows a color-coded backtest matrix over the meals of the last 90 days, independent of the analysis period (lookback 8/15/30 × half-life 1/2/3/5/7/14 × 25 %/configured/50 %/Zielband, all on the same meals; best cell = most in range, then fewest <80): simulated endpoint BG = `dose_target_mgdl` + (F − P) × Σ[g × KF]/10 (only the factor error; never add the measured g3, F already contains it) counted <80 / 80–160 / >160 mg/dL (fixed; Nightscout target range stays 80–180), plus typical factor deviation. The Zielband column (test only, never a suggestion) picks the P covered by the heaviest weighted set of past-factor intervals [F − (160 − target)·10/S, F + (target − 80)·10/S] for the tested meal's S; ties go to the region nearest the weighted median. The diary shows only the factor. An info-only analysis tile shows the work-stress surcharge for breakfast only (user request) over 30 days with free days as the base, work = free × (1 + surcharge) (overall median work ÷ median free − 1, plus per free day: median breakfast on the 2 nearest work days before and 2 after, ≤7 days away, ≥2 values, ÷ free factor − 1); it changes no suggestion. Lower IE/KE = less insulin = cautious side.
- Model equation: IE/KE = 10 × (ΔG + confirmed exercise glucose drop + Σ[rapid IE × time-specific KF]) / Σ[carbs in g × time-specific KF]. An exercise drop is a per-meal, user-confirmed mg/dL estimate for the meal window; it does not exclude the meal. Internally the drop is positive; racing (Rennsport, adrenaline) is a sport type whose default drop is negative (a BG rise). The UI shows the signed BG change (−40 lowers, +40 raises). Use Decimal arithmetic and show the inputs, endpoint, doses, assumptions and equation. Full effect of late insulin, full carb effect by the endpoint, and no background glucose drift are **model assumptions**, not physiological facts or dosing advice.
- The app runs locally via docker compose up -d --build at 127.0.0.1:8765 using deployment environment variables (no env_file); keep Docker/VPS deployment viable. Python standard library serves the API and static site. Run python3 -m unittest discover -s tests -v and node --check web/app.js after calculation or UI changes.
