# Project context for future agents

- Language: everything written into the repository or onto GitHub is English: commit messages, PR titles and descriptions, review and issue comments, code comments, docstrings, test names, docs (docs/, AGENTS.md) and log messages meant for developers. German is used only in the conversation with the user, in the German UI and server texts (web/i18n/de.js and the German side of `tr()`/`pick()`, see below), in README.de.md as the German version of README.md, and for UI labels and domain terms quoted in English text ("Wirkt noch", KE, IE, KF), which stay as the UI shows them. Older German commits and PRs stay as they are; translate German comments or docs you touch.
- Purpose: German private diary and analysis web app for reviewing meal-specific insulin factors from FreeStyle Libre 3 Plus CGM data and manually injected Fiasp. The UI speaks German (default and reference) and English: every text the page shows lives in web/i18n/de.js and web/i18n/en.js under a key, and components call `t("area.key", { name })` from web/ui/i18n.js (`tx` when a placeholder is markup, `{ one, other }` for plurals, `locale` for number and date formats, `UNIT` from lib.js for IE/KE vs U/CU). A new text gets a key in both files; a key missing in English falls back to German. Static texts in index.html carry `data-i18n` / `data-i18n-<attribute>`; login.html has its own two-language snippet. The language follows the browser unless picked under Mehr → Sprache (stored per device, the page reloads). The server's own texts (error messages, hints in day and analysis data, Pushover messages, the meal agent's prompts and tool descriptions, MCP instructions) follow `APP_LANGUAGE` (de default, en) via app/i18n.py: write the German text and wrap it as `tr("Text mit {name}", name=…)`, add its English to app/i18n_en.py (tests/test_i18n.py fails on a missing one); a whole prompt picks one of two versions with `pick(de, en)`. Text written into Nightscout or matched when reading it back keeps a language-independent marker (sport notes are stripped in either spelling, episodes.NOTE_LABELS). The read API's documentation (app/tables.py) stays German.
- Nightscout is the exclusive source of truth for CGM readings, carbs, injections and the time-specific correction-factor (`sens`) schedule. SQLite mirrors source data, caches the current Nightscout profile for local analyses and stores versioned calculation-model settings. Apply the current profile schedule to all analyses; do not reconstruct historical profile schedules. Calculated meal factors are never written to Nightscout; each calculated diary day is stored in SQLite (`day_results`) with a fingerprint of everything it reads plus a hash of the app's code, and is recalculated whenever that fingerprint changes. Credentials and app login come from deployment environment variables, never tracked files. SQLite remains on the persistent data mount.
- CGM readings: since 2026-10-26 the LibreLinkUp uploader also sends LibreLinkUp's smoothed history (about every 5 min a reading 1–9 s after a live one, without `direction`). `episodes.normalize_entries` drops a reading without `direction` within 10 s of one with it, so every calculation, chart and the read API see only live readings; a lone history reading still fills a gap. The mirror keeps Nightscout's rows unchanged.
- Insulinfaktor means **IE per KE**, with 1 KE = 10 g carbohydrate (KE = Kohlenhydrateinheit). Korrekturfaktor is separate, time-specific **mg/dL per IE**. Nightscout I:C is g/IE = 10 / (IE/KE).
- One factor is calculated for each breakfast, lunch or dinner window. Sum **all** recorded carbohydrate events and **all full rapid-insulin IE** from meal start up to, but not including, the endpoint. Split boluses and later corrections count in full even minutes before the endpoint; basal insulin does not count. Rapid injections before the window count with the share of their effect that acts between window start and endpoint: the dose help subtracts that insulin as "Wirkt noch", so without it the factor of such meals was too small and the insulin was deducted twice. A migration moved an `auto_percentile` of 40 to 35 with it so the mean dose stays level. Do not revive the former triangular Fiasp action weighting; legacy peak/duration settings are ignored.
- Pre-bolus: a rapid dose without carbs at most 30 min (`PREBOLUS_LEAD`) before a main meal whose own entry has no rapid insulin starts that meal's automatic window (earliest such dose), so it counts in full and ΔG is measured from it; not when carbs lie between dose and meal or an earlier main meal's automatic window still holds the dose (then it is that meal's correction). Endpoint, the 120-minute rule and snack grouping stay relative to the meal time; `auto_start`/`prebolus` in the calculation show it.
- Default endpoint: meal start + 180 minutes. Every rapid-insulin dose inside the window (before the next main meal) extends the endpoint to that dose + 180 minutes, so late corrections get a full window to act. If the next main meal is >120 minutes after meal start and before that (possibly extended) endpoint, use the last valid CGM value within 15 minutes before it. If a second main meal cannot be separated this way, show a blocker. CGM values at exact endpoints are linearly interpolated with a maximum 15-minute surrounding gap.
- A user can persist a manual window per meal in SQLite (`analysis_windows`: meal start − 2 h ≤ start ≤ meal start + 2 h, end ≥ max(meal start, start) + 30 min, at most 10 h long). It replaces the automatic start/endpoint for that meal only; the meal's own entry (carbs and its bolus) always counts even if the start lies after it; the same half-open counting, full-dose rule and second-main-meal blocker still apply. It is never written to Nightscout.
- A new diary carb entry < 120 min after the previous main meal start (across the clock-based breakfast/lunch/dinner boundary), or inside the (extended) window of a main meal of the same kind, is a snack of that meal. The entry form shows this as a chip the user can flip to "own main meal" (`[DA2:meal]` marker), which keeps it a separate root. Each meal kind counts at most once per day: a diary carb entry whose clock-based kind already has a main meal that day is a snack, of the preceding meal by the rules above or else of no meal, and cannot be flipped to its own meal. A new diary carb entry below 20 g that would start a main meal defaults to a snack of no meal and can be flipped to its own meal. A stored diary snack (`[DA2:snack]`) whose meal became a snack of no meal this way is classified afresh on day load and can become the main meal itself (13.10.: 12:20 is lunch); other stored snacks stay snacks. A snack the form assigns to a preceding main meal can instead end that meal: while the entry lies inside the meal's window and a manual window from its current start to the entry passes the manual-window limits, the assignment carries `close`; a "<Mahlzeit> hier abschließen" chip (payload/MCP `close_meal`) makes the entry a snack of no meal and saving stores that manual window (the same as "Zeitraum anpassen"), so the snack and later entries no longer count. A meal whose manual window ended before a new entry takes no snacks.
- Day type (work/free) applies to breakfast and is optional (setting `day_types`, the user 2026-11-26 for open source: off for a new installation, a settings version from before the switch keeps it on; off means marks.analysis_day_types() returns None, day_type_for gives (None, "off"), breakfast is one Automatik key like lunch and dinner, the entry form, "Verlauf" and the analysis hide Arbeit/Frei and the stress tile); while on, the entry form asks for it only before breakfast end while the day has no carb entry yet, afterwards it is changed in "Verlauf": manual per-day choice (`analysis_day_types`) > open vacation period (`vacation_periods`, toggled in settings) > Mon–Fri work. Vacation meals: every day inside a vacation period carries `vacation` (day payload, each meal, read API `meals.vacation`, "Urlaub" badge in "Verlauf"), independent of a manual day type; the switch can name the first vacation day or the first day back up to 14 days ago (POST /api/vacation `day`). Setting `auto_vacation` (factors.counted_days) decides how the Automatik, the breakfast day-type median, the place factor, "Wirkt noch", early warnings and the analysis backtest read them: `separate` (default) counts every day during a vacation and, outside one, skips vacation days and moves the days before them up by the vacation's length (meal points carry the counted `day` and the calendar `real_day`), so after coming home lookback and half-life reach the meals before the vacation; `vacation_only` additionally counts only vacation days during a vacation (the lever for vacation-specific adjustments after a few days); `all` treats vacation like any day. Before breakfast end, dose help uses the median breakfast IE/KE of that day type from the past 28 days when ≥3 valid non-excluded meals exist, else Nightscout I:C.
- Calculated fat/protein surcharge: with the agent's fat_g/protein_g in the entry payload and the surcharge method, the dose help returns `surcharge_choice` (static vs. calculated: FPE = (9·fat + 4·protein)/100, `fpe_surcharge_mgdl` (default 20) × FPE, max 200, acting linearly from the meal start until 3 h + 30 min·FPE, max 8 h) and uses the calculated one when the form sends `surcharge_mode: "fpe"` (main meals only). Then the split is "carbs now, surcharge later" (later part = surcharge IE; offered below split_min_grams once ≥ 2 IE), and saving writes `[DAZ:<mgdl>@<minutes>]` to the meal's note (`episodes.surcharge_plan`, treatment key `surcharge`, meal key `fpe_surcharge`), which on_board.sources and forecast.meal_surcharge use instead of the static surcharge for that meal. Edits keep the marker unless they send `surcharge_mode`: the meal card (entry-card.js, choice shown when /api/agent/session returns `fpe` for the entry, with the static surcharge beside it as `static_mgdl` plain/fat) sends "fpe" or "static", and diary.save_diary_treatment then computes the marker from the linked (or just refined) agent session or removes it; day timeline rows carry `surcharge`. Every reader of the calculated surcharge (dose help, entry save, meal card edit, agent session view) goes through fpe.estimate (which also checks the surcharge method), fpe.plan and fpe.view; add no second calculation. The entry form and the meal card show the choice with the same component (web/ui/meal-fields.js `SurchargeChoice`). The entry form remembers the last choice in localStorage. Fat/protein level: the Fettreich chip is gone from the entry form, the meal card and the meal chat (old `[DAQ:fat]` marks are still read and kept); a carb entry without the agent's estimate instead picks Nichts / Normal / Fett (web/ui/meal-fields.js `FatLevel`, payload `fpe_level`), which fpe.estimate turns into 0 / 4 / 10 FPE (fpe.LEVELS: Normal and Fett equal the former static 80 and 80 + 120 mg/dL at 20 per FPE) and which is always used (fpe.chosen) and saved as `[DAZ]`; dose help says `surcharge_levels` while the surcharge method is on, day timeline rows carry `fpe_level` (fpe.level_of: from the [DAZ] duration, else the fat mark), and the card sends a changed level only. A recheck on 28 vacation meals with the agent's estimate found no link between estimated FPE and the needed insulin, so `fpe_surcharge_mgdl` stays 20 for now; removing the static surcharge and its Automatik row is due for review 30 days after the vacation.
- With carbs, dose help uses only the calculated auto factor and shows three suggestions with it: normal (corrects to `dose_target_mgdl`), cautious (corrects to `dose_cautious_target_mgdl`, default 140) and carbs only (carbs plus sport, no BG correction, needs no fresh CGM). While auto has <4 meals the breakfast day-type median or Nightscout I:C stands in, named in the factor line. Without carbs: normal and cautious correction. Auto uses the `auto_percentile` (25–50, default 37.5) of valid non-excluded IE/KE of the current meal kind (by clock; breakfast filtered by day type) from the past `auto_lookback_days` (8/15/30, default 30; 8 keeps the previous Saturday on Sunday; a stored 14 becomes 15, 21 or 28 becomes 30), each weighted 0.5^(age/`auto_half_life_days`) (default 7; weighted quantile = linear interpolation at (n−1)×p for equal weights, app/forecast.py), needs ≥4 meals. The former day shift (Tageslage) and equally weighted method were removed at the user's request. `auto_method` = `percentile` (default) or `surcharge`: each main meal has a meal surcharge Z = `auto_surcharge_mgdl` (fat/protein, default 40, 5–150), scaled by min(1, carbs/40 g); past factors lose 10·Z·share/S before the percentile, and the dose gives an entry the share its carbs add to what is still in the stomach, meal, snack or carbs alone, so the factor windows per main meal stay the only place where meal and snack differ. A main meal marked fat/protein carries `auto_fat_surcharge_mgdl` more, in the past factors, the dose, "Wirkt noch", early warnings and the backtest/tuning/trade-offs (only for surcharge variants > 0); meal points carry `fat` from the meal's quality mark. Place factor: a place with `adjust` (settings switch "Ortsfaktor") scales factor and surcharge of entries there by forecast.place_scale = weighted median (half-life 14 days) of actual ÷ Automatik-suggested factor of its main meals in the last 60 days (each suggestion recomputed for that meal's day without place factor), from 3 meals, clamped 0.5–1.5; the dose help uses the chosen or position-suggested place of the entry (`place_id`, "none" = none on purpose), "Wirkt noch"/warnings/effects scale the carbs and surcharge of entries recorded at such a place (factors.entry_scale); the factor line names it ("Ort Kantine −13 %"), the place settings show the current value. Switching it on for every place made the backtest worse (Zuhause/Büro), so it stays opt-in. Meals at such a place (`own_place` on the meal points) stay out of every Automatik history (base factor, backtest, examples), so they neither pull down the others' factor nor shrink their own place factor through it (user question 2026-11-06); the place factor is measured against the factor of the other meals. The analysis page has two sub-tabs: Werte (period-based values) and Automatik: a worked example per meal kind (factor, typical meal, KE × factor + surcharge), current strategy vs. the trade-off line of all option combinations (not beaten on both <80 and >160; forecast.tradeoffs), one row per setting with only that setting varied (percentile 25/30/35/40/45/50, surcharge off/20/40/60/80, half-life, lookback; each row on the meals all its options can predict; verdict better/shift/none beyond max(2 meals, 5 %); forecast.tuning), and an "Übernehmen" per option that saves the setting change the server attached. Collapsed below it shows the color-coded backtest matrix over the meals of the last 90 days, independent of the analysis period (lookback 8/15/30 × half-life 1/2/3/5/7/14 × 25 %/configured/50 %/configured + surcharge, all on the same meals; best cell = most in range, then fewest <80, highlighted per lookback period and overall): simulated endpoint BG = `dose_target_mgdl` + (F − P) × Σ[g × KF]/10 (only the factor error; never add the measured g3, F already contains it) counted <80 / 80–160 / >160 mg/dL (fixed; Nightscout target range stays 80–180), plus typical factor deviation. The surcharge column predicts P = percentile of (F − 10·40·share/S) + 10·40·share/S of the tested meal (the former Zielband column was replaced at the user's request). The diary shows only the factor. An info-only analysis tile shows the work-stress surcharge for breakfast only over 30 days with free days as the base, work = free × (1 + surcharge) (overall median work ÷ median free − 1, plus per free day: median breakfast on the 2 nearest work days before and 2 after, ≤7 days away, ≥2 values, ÷ free factor − 1); it changes no suggestion. Lower IE/KE = less insulin = cautious side.
- The lower target (option "Tiefer", `dose_low_target_mgdl`) was removed as a concept on 2026-11-26 at the user's request; a stored value is dropped by config. Since 2026-11-15 the entry form shows a dose slider instead of option buttons (app/correction_scale.py `dose_range`, `dose.slider`); `cautious` and `carbs` are no longer shown there. A "0" button left of the slider sets no insulin with one tap (`slider.zero`, the readout shows where glucose lands at 0 IE); moving the slider or typing IE leaves it, a second tap goes back to the recommendation.
- Dose help subtracts what still acts: rapid insulin of the last 6 h with the active insulin profile (app/insulin.py, `APP_INSULIN`, upstream only `fiasp`: Loop's exponential curve, peak 55 min after 10 min delay, 6 h; a fork adds another profile there, and the profile key is part of every day's fingerprint; in the meal factor only for injections before the window, doses inside it count in full) × KF at the dose; carbs digested in one stomach: every carb entry reaches it 15 min after its time, it passes on 1 g/min × S/(S + 40 g), shared by all entries in it (on_board.stomach), valued at the Automatik factor of the entry's clock-time meal kind (else Nightscout I:C) × KF; with the surcharge method each carb entry carries Z × (share(stomach + carbs) − share(stomach)), linearly from the entry over 5 h (6 h with its fat mark, the calculated fat/protein surcharge over its own minutes). 3-h forecast over 60 days: MAE 50.5 instead of 51.7 with the former rules. Normal (and carbs only) corrects the full forecast BG − insulin rest + carbs/surcharge rest; cautious uses that forecast minus its typical miss (60 mg/dL), at least the BG where the rests only cancel active insulin, and the cautious target; below 70 mg/dL the same forecast applies (the former guard that only let the rests cancel active insulin was removed at the user's request 2026-10-23: it ignored a hypo snack and still subtracted the full correction, 0.5 instead of 1.5 IE for 34 g at 68 mg/dL). The diary's "Jetzt" overview shows a "Wirkt noch" card from the preview's `on_board`. Curve shape, absorption times and surcharge window are re-estimated offline by Claude, not in the app.
- Split bolus: from `split_min_grams` (default 80, 0 off) carbs on a main meal (never a snack) the entry form preselects a "Split" chip, unless the normal option's full dose is below `split_min_units`: then no chip and no split (split.worth_it, decided in entry._dose); each option then shows `split_first_percent` (default 60, rounded to 0.5 IE) now and the rest at meal + `split_delay_minutes` (default 120). Saving today stores the chosen option's full dose − entered IE as `[DASP:<IE>@<min>]` in the meal's Nightscout note. The plan stays open until a rapid dose without carbs >15 min after the meal or 3 h past due; meanwhile the "Wirkt noch" card names it (not in the forecast) and an entry without carbs offers a "2. Teil" option first, next to normal/cautious from the current forecast. Dynamic second part: its amount is the current forecast's correction (= normal; the planned IE only as orientation, or as amount without fresh CGM); it is due early 60 min after the meal until 15 min before the planned time when BG ≥180 and rising ≥15 mg/dL per 15 min, and at the planned time it waits while BG <110 or falling >5 mg/dL per 15 min, at most 60 min. The split push follows that state (one per plan, naming forecast and planned IE). Carbs while a plan is open: dosing.suggest `hold_rise` caps the start glucose of every option at its target (normal/carbs `min(forecast, target)`, cautious `min(cautious forecast, cautious target)`), so the entry doses its own carbs and corrects only downwards; the forecast's rise stays with the second part, the expected values assume it, the form names the open part (dose.js), and such a dose with carbs does not close the plan (split.open_plan).
- Calculation rules live only in Rust (core/, see core/README.md and docs/architecture.svg; user decision 2026-11-27: no rule implemented twice). Python in app/ is the outer layer: web server, APIs, Nightscout sync, storage, LLMs, texts. The server calls the core through the PyO3 module core/diabetes-core-py (built with `python3 core/build.py` into app/diabetes_core.abi3.so, gitignored; the Dockerfile builds it in a Rust stage); app/core.py is the only bridge: `core.call("module.function", **args)` sends JSON (Decimal and datetimes as text) and decodes the result with app/core_types.json (Python types per function and JSON path; add an entry by hand for a new core function). app/calculation, episodes, on_board, dosing, split, correction_scale, fpe, glucose, glucose_alerts, correction_check, forecast and analysis/stats keep only their names, signatures and docstrings and call the core; app/services/dose_help.py only gathers a snapshot for `services.dose_help`, day_view.compute_day one for `day.compute_day` (day_view.day_snapshot) and summary.compute_summary one for `summary.compute_summary` (summary.summary_snapshot, with the meal points from `factors.meal_points`); analysis/night.py, sport_analysis.py, factors.counted_days/meal_points/place_scales/meal_surcharge_mgdl, day_view.with_checks and summary.suggestion_miss/miss_trend/history_days are wrappers too; services/notifications.py is the adapter of `notifications.due` (core notifications.rs decides which push reminders are due and their texts; Python gathers the dose help's snapshot, today's basal, switches, pauses and send times, checks sent keys and sends). A new or changed rule is written in Rust, never in Python. Still in Python and to be moved to Rust: the entry form's rules (services/entry.py), diary edits, the window editor, dishes.py outcome rules. core/golden/calls.jsonl.gz holds calls recorded once from the former Python reference (synthetic test data only; never record from a real database) and CI replays them (core/golden/compare.py, numbers within 1e-9 relative, doses and decisions exactly); Python tests compare Decimals with a tolerance where rust_decimal differs in the last digit. Rust uses rust_decimal and typed structs, not a copy of Python's Decimal quirks.
- Maintainer workflow: the maintainer does not review code line by line; once CI is green, Claude merges its own PRs.
- Model equation: IE/KE = 10 × (ΔG + confirmed exercise glucose drop + Σ[rapid IE × time-specific KF]) / Σ[carbs in g × time-specific KF]. Sport counts automatically: each Exercise session lowers glucose by its drop linearly from its end over its kind's duration; a session entered up to 6 h ahead counts in full. It is part of what still acts: "Wirkt noch", every dose option incl. pure corrections, and the early warnings. The meal factor's drop is each session's share acting between window start and endpoint × its drop, always automatic: the effect belongs to the session only, the per-meal own value / "Kein Einfluss" and POST /api/analysis/sport were removed. The day payload's exercise items carry `sport_shares` (per meal window the share it gets), `sport_rest_mgdl` (between or after meals) and `sport_effect_until`; web/ui/sport.js (`SportEffectFields`, `SportShares`, `sportSummary`) draws and sets it identically in the entry form, the entry card and Verlauf. The entry form no longer asks about sport at meals, and sport is never an open review item. `sport_lookback_minutes` only links sessions to meals in the sport analysis. Internally the drop is positive; racing (Rennsport, adrenaline) is a sport type whose default drop is negative (a BG rise). Sport kinds: the four built-in ones (episodes.SPORT_LABELS, translated names) plus the user's own (setting `sport_custom`, key `own_<n>` -> name, Profil & Modell → Sport, each with effect and duration like the built-in ones); a kind is never deleted, only hidden from the entry form (`sport_hidden`), so recorded sessions keep their name and effect. Names always come from the current settings (episodes.sport_names / note_labels), effects from the day's settings version; MCP `sport_kind` takes a key or a name; the page reads them through lib.js `setSportKinds`, `sportKinds` (offered), `sportNames` (all) and `sportOptions`. The UI shows the signed BG change (−40 lowers, +40 raises). Use Decimal arithmetic and show the inputs, endpoint, doses, assumptions and equation. Full effect of late insulin, full carb effect by the endpoint, and no background glucose drift are **model assumptions**, not physiological facts or dosing advice.
- Basal is the one injection stored locally first and mirrored to Nightscout as a `Note` with `basal_units` and `[DA2:basal]`, never with an `insulin` field (Nightscout IOB and the meal factor must not count it). Unsent doses are retried on day load; a synced dose missing from a fresh Nightscout read is dropped; untracked Nightscout basal notes are adopted. Before breakfast end the entry form offers a preselected chip with `basal_default_units` (default 0 = off) while the day has no basal; a separate Basal entry mode records any amount. Groundwork for adjusting basal automatically later.
- Carb entries can carry a three-level carb certainty `[DAQ:weighed]` (gewogen), `[DAQ:known]` (halbwegs sicher: known dish or FDDB AI), `[DAQ:unsure]` (no serious estimate; older unsure marks keep this meaning), API field `carbs_certainty`; the levels were redefined 2026-11-17 for new entries and the meal agent: weighed = gewogen oder genormt (package, standard portion), known = all relevant ingredients known and only the weight estimated, unsure = unknown ingredients or a very unclear amount; plus the meal factors `[DAQ:fat]` (fett-/eiweißreich) `[DAQ:alcohol]` and `[DAQ:fast]` in the Nightscout note, picked as icon chips in the entry form (the Alkohol chip and MCP argument were removed 2026-11-15 at the user's request; old marks are still read, shown and kept on edit) and shown as icons on the meal, entry and recent chips; a meal shows the least certain level of its marked counted carb entries and each factor when any entry has it. They are recorded and exposed via the read API only and change no calculation until the user approves a use.
- Eating places: a place is a chip (Büro, Zuhause, Kantine) with any number of spots the user defines themselves in settings, a "Schnellauswahl" switch (quick places get their own chip in the entry form, the others sit behind "Weitere") and a "Standard woanders" switch for at most one place (Auswärts; the migration marks a place named Auswärts) (`places`, `place_spots`, app/places.py, app/services/places.py). For a carb entry timed within 30 min of now, the browser position (fix within 30 min of the entry time; accuracy ≤250 m) preselects the chip of the nearest spot holding it, else the fallback place; the user can flip it. The position only picks the chip: it is never stored and never teaches a spot (the former stored positions, unknown-position groups and learning were removed 2026-10-29). Only the chosen place is stored per diary entry by its `[DAE:…]` event id in SQLite (`entry_locations`, lat/lon columns stay empty), never in Nightscout; deleting a place takes it off its entries. The edit dialog sets a place afterwards; meals show their own entry's place (else the first counted carb entry's), and an entry inside a meal in "Verlauf" shows its place and carb certainty only where they differ from the meal head; read API `place` on meals and treatments, MCP `place` by name. Recorded only, changes no calculation until the user approves a use.
- Blood glucose measured by hand: the entry form's "BZ blutig" field (open by itself while there is no fresh CGM value) and MCP `finger_mgdl` save a Nightscout `BG Check` (glucoseType Finger, mg/dL, `[DAE:…]`), also without carbs or insulin. Dose help uses a BG Check (or the typed value at the entry time) as start glucose when it is newer than the latest CGM value, same 15-minute freshness, no trend. When the meal-window start has no interpolable CGM value, the nearest BG Check within 15 minutes is the meal factor's start glucose; otherwise CGM always wins. The CGM curve, endpoints and other analyses never read it.
- An entry is always timestamped now unless the user changes the time on purpose. The manual time is dropped after a saved entry, a day or view change, or 10 minutes without touching the entry form; while it is untouched the field follows the clock (refreshed every 30 s and when the tab becomes visible again), so a stale timestamp cannot ride along on the next entry.
- Dishes and the meal agent. Dishes: every carb entry can carry a dish (`dishes`, chosen by name, a new name creates it) and a free description, stored locally by event id (`meal_records`), never in Nightscout; rules in app/dishes.py, catalogue in app/services/dishes.py (GET/POST /api/dishes, Analyse tab "Gerichte": rename, category, archive, merge, delete). Outcome of a dish: `ratio` = median of (meal factor ÷ median factor of the same meal kind in the 30 days before, ≥4 meals) over its valid main meals, named from 3 meals; typical carbs = median of its last 5 entries; effective carbs = typical × ratio. No dish picker in the entry form; dish and description are added or changed in "Verlauf" (edit dialog, also for entries made offline). No retro-labelling of old meals. Read API `/api/v1/meal-records` and `/api/v1/dishes`, `dish` column in meals/treatments; MCP `list_dishes` and `save_entry` args `dish`/`description`. Agent (app/meal_agent.py rules and prompt, app/services/agent.py, app/store/agent.py, app/ingestion/llm.py): "Essen einschätzen" in the entry form and the edit dialog takes up to 4 photos and text, and returns carbs with range, items, certainty, the matching dish, reasoning, one optional question and web sources; follow-ups continue the session. Design decisions: the agent estimates carbs only and never names insulin, the dose stays with the dose help; when a dish kept needing more insulin than usual its carbs were probably underestimated, so the agent raises its estimate with the dish history (`history_adjustment_g`); tuning split intervals is a later idea. The agent should work freely; a dish is defined by its main carb source (rice with whatever beside it is one dish), matching is generous, the whole catalogue serves as reference even without an exact match, and web search is used freely (up to 8 searches). Providers are chosen in settings (`agent_settings`): Claude, OpenAI, OpenRouter, keys only from the deployment (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY`); calls go through the vendor SDKs. The agent sets fat_protein only for truly fat-rich meals with a lasting BG effect such as pizza or steak, not for pho or curry with rice. Correcting an eaten meal afterwards: the edit dialog's agent button continues the estimate linked to that entry (GET /api/agent/session?event_id=, photos and turns kept), the answer always describes the whole meal, and "Übernehmen" plus saving updates carbs, description and the record the agent later uses as reference. A dish is mostly defined by its main carb source (rice with whatever beside it is one dish), and similar dishes and meals serve as reference without an exact match; web search is optional per provider.
